# Chatbot Endpoint — Technical Specification

## 1. Overview

This document specifies the design and implementation requirements for a chatbot endpoint that handles user queries related to expenses and user data. The chatbot will operate as an independent module, built on the LangGraph framework, with persistent conversation history stored in PostgreSQL.

---

## 2. Scope

The chatbot endpoint will:
- Accept natural language (text) queries from external systems.
- Process queries related to expenses and users.
- Maintain conversational context (memory) across multiple turns using a `conversation_id`.
- Return responses as a stream.
- Persist all chat interactions (user and AI) to a PostgreSQL database.

This endpoint is **not** part of the existing expense or user endpoints and will be exposed as a separate, standalone API.

---

## 3. Endpoint Details

| Attribute | Value |
|---|---|
| **Path** | `/chatbot/queries` |
| **HTTP Method** | `POST` |
| **Response Type** | Streamed (e.g., Server-Sent Events / chunked transfer encoding) |

---

## 4. Request Specification

### 4.1 Request Payload

| Field | Type | Required | Description |
|---|---|---|---|
| `text` | String | Yes | The user's query in natural language text format. |
| `conversation_id` | String | Yes | Identifier used to associate the query with an existing conversation and retrieve relevant context/memory. Always supplied by the client, including for the first message of a new conversation (the client is responsible for generating it, e.g., via UUID). |
| `user_id` | String / Integer | Yes | Identifier of the user making the request, obtained directly from the request body. |

**Sample Request Body:**
```json
{
  "text": "What were my total expenses last month?",
  "conversation_id": "conv_12345",
  "user_id": "user_6789"
}
```

---

## 5. Response Specification

### 5.1 Response Behavior
- The response will be streamed back to the client using **Server-Sent Events (SSE)** as it is generated by the underlying LangGraph agent.
- The stream will contain the AI-generated response text corresponding to the current query only. Retrieval of the full conversation history is handled by a separate endpoint (see Section 5.3).

### 5.2 Sample Streamed Output (conceptual)
```
data: {"chunk": "Your"}
data: {"chunk": " total"}
data: {"chunk": " expenses"}
data: {"chunk": " last month..."}
data: [DONE]
```

### 5.3 Conversation History Retrieval Endpoint

Since `/chatbot/queries` only streams the response to the current query, a separate endpoint is required to fetch the full conversation history.

| Attribute | Value |
|---|---|
| **Path** | `/chatbot/conversations/{conversation_id}/history` |
| **HTTP Method** | `GET` |
| **Response Type** | Standard JSON (non-streamed) |

**Sample Response:**
```json
{
  "conversation_id": "conv_12345",
  "messages": [
    { "role": "AI", "message": "Your total expenses last month were $450.", "date": "2026-09-12T10:15:32Z" },
    { "role": "USER", "message": "What were my total expenses last month?", "date": "2026-09-12T10:15:20Z" }
  ]
}
```

> **Note:** Path/method naming above is a suggested convention; confirm against existing API naming standards before implementation. Message ordering (most recent first vs. chronological) should also be confirmed.

### 5.4 List Conversation IDs Endpoint

For a sidebar-style conversation list, a client needs every `conversation_id` a
user has messages in, without pulling each conversation's full message
history.

| Attribute | Value |
|---|---|
| **Path** | `/chatbot/fetch_all_conversation_ids` |
| **HTTP Method** | `GET` |
| **Query Parameters** | `user_id` (required) |
| **Response Type** | Standard JSON (non-streamed) |

Returns every distinct `conversation_id` that has at least one `chat_history`
row for `user_id`, each with its creation timestamp (the timestamp of that
conversation's first message), ordered by creation timestamp **descending**
(most recent conversation first) so a frontend can render it directly as a
chronological sidebar.

**Sample Response:**
```json
{
  "user_id": "user_6789",
  "conversations": [
    { "conversation_id": "conv_12345", "created_at": "2026-09-12T10:15:20Z" },
    { "conversation_id": "conv_98765", "created_at": "2026-09-10T08:02:11Z" }
  ]
}
```

A `user_id` with no conversations returns `200` with `conversations: []`,
not `404` — consistent with 5.3's empty-history behavior.

## 6. Technical Framework

- **Core Framework:** LangGraph
- **Capabilities Required:**
  - **Memory:** Retain and utilize context from prior turns within the same conversation.
  - **Conversation History Management:** Retrieve and incorporate historical messages tied to a given `conversation_id` to maintain contextual continuity.

---

## 7. Data Persistence

### 7.1 Database
- **Type:** PostgreSQL

### 7.2 Table: `chat_history`

| Column | Type (suggested) | Description |
|---|---|---|
| `id` | UUID / Serial (Primary Key) | Unique identifier for each chat record. |
| `message` | Text | The actual message content (user query or AI response). |
| `date` | Timestamp | Date and time the message was created. |
| `user_id` | String / Integer | Identifier of the user who initiated the conversation. |
| `conversation_id` | String | Identifier grouping messages belonging to the same conversation. |
| `role` | Enum / String | Indicates message origin: `USER` or `AI`. |

**Role Values:**
| Value | Meaning |
|---|---|
| `USER` | Message sent by the end user. |
| `AI` | Response generated by the chatbot. |

Each turn of the conversation (user query + AI response) will result in two rows being inserted into `chat_history`, one for each role.

---

## 8. Error Handling

| Scenario | Behavior |
|---|---|
| **Empty / missing `text`** | Return `400 Bad Request` with a validation error message before invoking LangGraph; no row is written to `chat_history`. |
| **Missing `conversation_id` or `user_id`** | Return `400 Bad Request` with a validation error message, since both fields are mandatory. |
| **Invalid / expired `conversation_id`** (not found in `chat_history`) | Treat as the start of a new conversation under that `conversation_id` rather than rejecting the request, since no server-side expiry concept currently exists. *(Confirm this assumption — the alternative is to return `404 Not Found` if strict validation is preferred.)* |
| **LangGraph / agent processing failure** | Terminate the SSE stream with a structured error event (e.g., `data: {"error": "Processing failed, please retry."}`) followed by `[DONE]`; return `500 Internal Server Error` if the failure occurs before streaming begins. |
| **DB write failure (chat history)** | Log the failure server-side; the response to the client is not blocked or failed solely due to a persistence error, but the failure should be logged/alerted so history isn't silently lost. *(Confirm whether a failed write should instead fail the request — depends on how strictly history is relied upon downstream.)* |
| **DB read failure (history retrieval endpoint)** | Return `500 Internal Server Error` with an appropriate error message. |
| **Missing `user_id` (list conversation IDs endpoint)** | Return `422 Unprocessable Content` — it is a required query parameter. |
| **`user_id` with no conversations (list conversation IDs endpoint)** | Return `200 OK` with `conversations: []`, not `404` (section 5.4). |

---

## 9. Summary

This chatbot endpoint will provide a dedicated, streamable, memory-aware conversational interface for expense and user-related queries, built on LangGraph, with all conversation turns persisted in a structured PostgreSQL table for auditability and context retrieval.
